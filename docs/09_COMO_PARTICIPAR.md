# Cómo participar en ALM- | Guía para la comunidad

## 1. Consulta libre

Cualquier persona puede leer https://github.com/AntonioLopezM/ALM- sin iniciar sesión. El acceso a los documentos publicados no requiere permiso individual ni cursar formación previa.

## 2. Proponer, comentar y revisar

**Canal de entrada:** https://github.com/AntonioLopezM/ALM-/issues

GitHub Issues está habilitado en el repositorio. Para abrir una incidencia se requiere una cuenta GitHub. Sugerimos indicar en el título una categoría:

- **[Pregunta]**: término, definición, lectura o relación que convendría aclarar.
- **[Corrección]**: error demostrado, fuente incorrecta o contradicción documental.
- **[Prueba]**: enunciado preciso, hipótesis y demostración o contraejemplo.
- **[Educación]**: mejora del curso ALM / autocuidado / «expertar medio».
- **[Traducción]**: mejora de accesibilidad lingüística y claridad.
- **[Colaboración]**: propuesta pública de cooperación dentro de la información no sensible.

### Ficha mínima recomendada

1. Qué documento o afirmación se evalúa, con enlace.
2. Qué se propone, pregunta o corrige.
3. Qué evidencia o explicación lo respalda.
4. Qué sigue siendo incierto.
5. Qué tipo de ayuda o revisión se solicita.

No todos los participantes necesitan conocimientos técnicos: explicar una dificultad de comprensión también es una contribución.

## 3. Cambios en documentos

Se pueden proponer cambios mediante Pull Requests de GitHub. Los cambios deberán preservar procedencia, atribución, estado de evidencia y límites de cada afirmación. **No publicar archivos privados, datos personales, resultados sin permiso ni experimentos peligrosos.**

La propuesta de una modificación no implica su aceptación ni concede permiso para usar la propiedad intelectual de terceros.

## 4. Participación con respeto

Se anima a discrepar con argumentos, preguntar sin vergüenza y reconocer correcciones. No se admiten acoso, ataques personales, discriminación ni atribuciones de apoyos inexistentes.

La participación internacional debe facilitar diferencias de idioma, experiencia, acceso y formación. Las contribuciones sustantivas deben ser reconocidas.

## 5. Desarrollo y acceso restringido

La colaboración sobre documentación pública y el curso introductorio puede plantearse en abierto. Cualquier revisión de código computacional interno, datos sensibles o arquitectura reservada necesita **una autorización adicional explícita** y un alcance concreto. No usar Issues para solicitar claves, copias privadas o acceso a información personal.

## 6. Estados de una revisión

**Recibida → En estudio → Aclaración requerida → Evaluada → Incorporada / No incorporada / Pendiente de evidencia.**

Este es un protocolo editorial propuesto, **no** la promesa de que exista ya un equipo que gestione cada fase ni de que haya plazos de respuesta garantizados.
